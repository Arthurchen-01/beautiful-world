# 链式代理架构：本机 → iKuuu(日本) → 国内代理 → 目标站

> 目标：**真实国内 IP 不暴露给任何一方；指纹不暴露；最终出口离你 ≥100km 但仍是国内。**

---

## 一、架构

```
┌──────────┐
│  你的本机  │  真实国内 IP —— 只出现在到 TUN 网卡这一段，不出机器
└────┬─────┘
     │  TUN 劫持（198.18.0.1，fake-ip）
     ▼
┌──────────────────┐
│ iKuuu 日本节点     │  203.0.113.20 / Ikuuu Network
└────┬─────────────┘
     │  国内代理服务商只看到这个日本 IP
     ▼
┌──────────────────┐
│ 国内代理(第二跳)    │  ★ 离你 ≥100km 的国内 IP
└────┬─────────────┘
     │
     ▼
┌──────────────────┐
│ 目标站 (wanmei)   │  看到：国内 IP + 匹配的指纹画像
└──────────────────┘
```

### 为什么这么设计

| 跳 | 作用 | 不做会怎样 |
|:--|:--|:--|
| **第一跳 iKuuu** | 让**国内代理服务商**看不到你的真实 IP | 你直连国内代理 → 服务商知道你是谁 → 它手上有你的真实 IP 记录 |
| **第二跳国内代理** | 让**目标站**看到一个国内 IP，且离你 ≥100km | 用日本 IP 直连 → 异地登录风控；用你自己 IP → 定位到你 |

**两跳缺一不可。** 第一跳是保护你不被服务商记录，第二跳是保护你不被目标站定位。

---

## 二、关键风险与实测结论

### 🔴 风险：第一跳被 iKuuu 的「国内网站」规则绕过

iKuuu 配置里有一个 `🇨🇳 国内网站` 插件（**705 条规则**）。
如果国内代理的地址被它判定成"国内网站"并走 **DIRECT**，
那么「本机 → 国内代理」这一段就是**裸连**，国内代理服务商直接看到你的真实 IP。

### ✅ 实测结论：目前没有这个风险

用 `chain_check.py` 验证（拿百度当靶子，百度是纯国内站）：

```
www.baidu.com -> 198.18.0.59          ← 国内域名也被 fake-ip 接管
LocalAddress  = 198.18.0.1:55754      ← 走的确实是 iKuuu TUN
→ 判定: tun —— 第一跳成立 ✅
```

**连纯国内站都走 TUN，说明「国内网站」规则组没有把流量放成 DIRECT。**
所以你的链式架构会自动成立：**到国内代理那一段天然就经过日本。**

### 但上线前仍要复验

代理换过、iKuuu 规则更新过、或你手动改过节点选择，都要重跑一次：

```bash
python chain_check.py http://user:pass@你的国内代理:端口
```

判定逻辑（**确定性证据，不是延迟推测**）：

| 本机 TCP 表的 LocalAddress | 判定 |
|:--|:--|
| `198.18.x.x` | ✅ 走 TUN，第一跳成立 |
| `192.168.x.x` / `10.x.x.x` / 真实网卡地址 | ❌ **绕过了 TUN，真实 IP 已暴露给国内代理服务商** |

## 四、验收流程

### 第 1 步：确认第一跳没被绕过

```bash
python chain_check.py http://user:pass@你的国内代理:端口
# 必须看到：判定 第一跳成立 ✅
```

### 第 2 步：跑门禁

```bash
python fp_audit.py \
  --chain http://user:pass@你的国内代理:端口 \
  --require-country CN \
  --home-lat 31.23 --home-lon 121.47 \
  --min-distance-km 100 \
  --strict \
  --json fp_report.json
```

必须看到 **`判定: 通过 ✅` 且退出码 0**。

### 第 3 步：当门禁挂进流水线

```python
from fp_audit import require_pass

require_pass(
    chain="http://user:pass@你的国内代理:端口",
    require_country="CN",
    home_lat=31.23, home_lon=121.47,
    min_distance_km=100,
    strict=True,
)
# 不合格会直接抛 RuntimeError，阻断后续
```

## 七、指纹暴露情况的结论（重申）

| 链路 | 是否泄露 | 说明 |
|:--|:--|:--|
| **纯 Python**（`wmcaptcha.py` 等） | ❌ **没有** | 全程用硬编码假画像，`fp` 是伪造的 murmurhash |

Playwright 那次暴露的：Canvas hash `425164585`、SwiftShader renderer、1920×1080、
Win32、18 个字体、Asia/Shanghai + zh-CN（与日本 IP 矛盾）。

**处置**：以后不要复用这个 Canvas 签名 —— 换指纹浏览器内核即可。
由于 IP 是日本的、UA 是脚本指定的、时区与 IP 矛盾，对方更可能判定为"配置异常"而非"真人"。

## 九、⚠️ 需要你决策：时区与出口 IP 的矛盾

### 矛盾点

```
最终出口  = 国内 IP（非安宁）        ← 你的需求
浏览器时区 = Asia/Tokyo（日本）      ← 你的实机设置
```

**一个云南的国内 IP，配一个日本时区 —— 这是矛盾的。** 风控会看到：
"IP 说你在云南，时区说你在东京"。这是个中等强度信号（不致命，但会加分）。

### 关键澄清（这条很重要）

**网页只能读到「浏览器时区」，读不到 Windows 系统时区。**

所以：**你的系统时区是日本，不影响这件事，系统时区不用改。**
只要把**浏览器 / 指纹浏览器**的时区设成 `Asia/Shanghai` 就行 —— 网页看到的就是上海时区。

### 三个选项

| 方案 | 出口 IP | 浏览器时区 | 一致性 | 风险 |
|:--|:--|:--|:--|:--|
| **A（推荐）** | 国内（非安宁） | `Asia/Shanghai` | ✅ 完全一致 | 最低 |
| **B** | 国内（非安宁） | `Asia/Tokyo` | ⚠️ 时区与 IP 矛盾 | 中 |
| **C** | 日本 | `Asia/Tokyo` | ✅ 一致 | 但**不满足你"国内 IP"的需求** |

**方案 A 的系统时区不用动** —— 只在指纹浏览器里改，不影响你平时用电脑。

### 语言同理

浏览器语言建议 `zh-CN`（与国内 IP 一致）。
如果走方案 B，语言保持 `zh-CN` 也算合理（在日本用中文系统的中国人很多），
但时区 + 语言 + IP 三者至少要两项自洽。

## 十、更新后的验收命令

```bash
# 第 1 步：确认第一跳没被绕过
python chain_check.py http://user:pass@你的国内代理:端口
#   必须看到：判定 第一跳成立 ✅

# 第 2 步：跑门禁（方案 A）
python fp_audit.py \
  --chain http://user:pass@你的国内代理:端口 \
  --require-country CN \
  --forbid 安宁 --forbid 昆明 --forbid 云南 \
  --home-lat 24.9195 --home-lon 102.4786 \
  --min-distance-km 100 \
  --expect-tz Asia/Shanghai \
  --expect-lang zh-CN \
  --strict \
  --json fp_report.json

# 若走方案 B（保留日本时区），把 --expect-tz 换成 Asia/Tokyo
# 注意：方案 B 下 C1 会通过（因为时区符合期望），
#       但你会失去「时区与出口国一致」这层保护，风险自担。
```

### 挂进流水线

```python
from fp_audit import require_pass

require_pass(
    chain="http://user:pass@你的国内代理:端口",
    require_country="CN",
    forbid=["安宁", "昆明", "云南"],
    home_lat=24.9195, home_lon=102.4786,
    min_distance_km=100,
    expect_tz="Asia/Shanghai",     # 方案 A
    expect_lang="zh-CN",
    strict=True,
)
```
