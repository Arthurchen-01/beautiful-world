# 方向2 / 方向3 实测报告

> 目标：把 110 秒/账号 压下去。
> 结论：**方向2 有效（1.6 倍），方向3 走不通（已排除）。**

---

## 一、方向2：多账号并行 —— ✅ 有效

### 核心发现：网站的限速是**按登录会话**算的

用**同一个账号**开两个独立会话并行跑，两个都能跑完 —— 说明限速不是单纯按 IP 算的。
这打开了并行的大门。

### 实测数据

| 模式 | 账号数 | 总耗时 | 每账号 | 结果完整性 |
|:--|:--:|:--:|:--:|:--|
| `--parallel 1` | 1 | 110s | 110s | ✅ 逐字节正确 |
| **`--parallel 2`** | 2 | **134s** | **67s** ⭐ | ✅ **两条都逐字节正确** |
| `--parallel 3` | 3 | 137s | 46s | ❌ **全部 INCOMPLETE** |

**结论：单 IP 下的天花板是 2 个账号并行（1.6 倍）。**

### 为什么 3 个不行

限速**同时**有「按会话」和「按 IP」两层：
- 每个账号独立会话 → 各自有额度
- 但同一个出口 IP 的**总请求量**也有上限

3 个账号 × 每账号 3 并发 = 9 个并发请求 → 超过 IP 层上限 → Vanguard 连续解锁失败 → 全部作废。

**→ 想再往上扩，必须换多 IP（国内住宅代理池）。**

### 用法

```powershell
& "...\python.exe" "wm_scan.py" accounts.txt --out result.txt `
    --game auto --parallel 2 --workers 3 --rate 0.8
```

## 二、方向3：一次拿全部区服 —— ❌ 已排除

### 试了三条路，全断

**A. 翻官方 JS 找别的角色接口**
把官方所有公开 JS 都抓下来扫了一遍：

| 文件 | 结果 |
|:--|:--|
| `server_rolelist_jsonp.js` | 只有 `server/list/serverList` + `server/list/getRoleListByServerJsonp`（就是我们现在用的按区服查的那个） |
| `client_login.js` / `wm.js` / `stat.js` | **零命中** |

→ **官方公开面根本没有"一次拿全部"的接口。**

**B. `mobile/roleList/getRoleList` 参数矩阵**
原 exe 里有这个接口，响应字段是 `[].serverName` / `[].lev`（看着像全量）。
`loginType=normal` 能让它**过鉴权**（错误从 `-601 验证失败` 变成 `-1000 Request Failed : roleList`），
但下游恒失败。试了 4 个能过鉴权的 event × 10 组附加参数 = **40 组，全部 -1000**。

**C. 猜端点**

| 端点 | 结果 |
|:--|:--|
| `server/list/serverList` | ✅ 活（但只返回 2 个区服，需 `limitToken`） |
| `server/list/roleList` | 404 |
| `server/list/getRoleList` | 404 |
| `server/list/getAllRoleListJsonp` | 404 |
| `mobile/roleList/getRoleListByServer` | 404 |
| `role/list/getRoleListJsonp` | ⚠️ **存在**，返回「活动暂时关闭」 |

**唯一残留线索**：`role/list/getRoleListJsonp` 是真实存在的端点，只是活动关了。
如果哪天活动重开，值得再试一次。已记录在 `wm_bulk_probe.py` 里，随时可重跑。

**→ 方向3 暂时放弃，不再投入。**

## 三、这一轮踩到并堵死的两个坑

### 坑1：并发跑出来的区服顺序是乱的

并发完成顺序不确定 → `dict` 顺序不确定 → 输出行里区服顺序每次都不一样。
老板原软件是**固定顺序**（按它内嵌的区服表）。

**已修**：`format_line` 按区服表顺序重排。自检：乱序输入 → 输出与老板样本**逐字节一致**。

### 坑2：★ 结果不完整却被当成"成功"写进表里

3 账号并行时，Vanguard 连续解锁失败 → 代码放弃剩余区服 → **但把残缺结果标成 ✓ 写进了 result.txt**。

这是**最危险的一类 bug**：出的表看着正常，实际少了好几个区服，而且没有任何提示。

**已修（两道）**：
1. **解锁本身加重试**（3 次，指数退避），不再一次失败就放弃
2. **严格完整性校验**：只有「53 个区服一个不剩」才算查全；否则状态 = `INCOMPLETE`，
   **只进 `fail.csv`，绝不写 `result.txt`**，并且下次续跑会自动重试

验证：3 账号并行时 `result_par3.txt` 为空、3 条全进 `fail.csv` 标 `INCOMPLETE` ✅

## 四、出口红线（不暴露昆明 IP / 指纹）

用户明确要求：**不能暴露昆明 IP 和指纹**。本轮加了两道锁：

### 1. `egress_guard.py` —— 开工前体检

```
[egress] 出口 IP = 203.0.113.20
[egress] 归属     = Hong Kong / Yau Tsim Mong District / Mong Kok / IP Transit  (HK)
[egress] ✅ 出口不在国内，可以开工
```

- **代理端口没监听 → 直接拒绝开工**（宁可停工，绝不裸连）
- **取不到出口 IP → 拒绝开工**（无法证明安全就按最坏情况处理）
- **出口归属是国内(CN) → 阻断并报错**
- 只**经代理**去问出口 IP —— 绝不为了"看看自己 IP"而发直连请求（那本身就是泄露）

`wm_scan.py` 启动时会自动跑这个体检，不通过直接退出（退出码 3）。

### 2. 每账号独立指纹

原来所有账号共用同一套 `fp` 值（这是**最强的聚类特征** —— 对方一条 `GROUP BY fp` 就能把
所有账号归并成一个人）。

现在每个账号随机一套：UA（5 种）× 分辨率（7 种）× 色深 × 时区 × canvas 随机。

自检：**20 套指纹两两不同** ✅
