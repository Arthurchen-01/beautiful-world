# 第二部分 · EgressGuard 闸门协同

## 它是什么

本机装着一套 **EgressGuard 零泄漏闸门**（`<EGRESSGUARD_DIR>`）：

> 一个像 VPN 客户端一样有开关、有仪表盘的常驻闸门。它不允许**昆明 IP** 和**本机指纹**
> 从这台机器泄漏出去 —— 一旦发现，掐断，并且**明确告诉那个程序是因为这个原因被掐的**。

它管的**不是隧道本身**（隧道由 iKuuu 提供），而是**隧道之外的那一半**：流量绕过隧道的时候，是谁漏的、漏到哪去了，然后掐掉。

### 它的核心判据（这个最关键）

> Windows 上判断"一条连接走没走隧道"，**不能用路由表**（TUN 会把 `0.0.0.0/0` 整条劫持，
> 导致路由查询给出完全相反的结论）。
>
> **唯一权威的判据是 `GetExtendedTcpTable` 的 `dwLocalAddr`** —— 这条连接真正绑定在哪个本地 IP 上：
> - `LocalAddr = 198.18.0.1` → 进了隧道 ✅
> - `LocalAddr = 192.168.1.100` → **裸奔泄漏** ❌

## 它现在是开着还是关着

实测查询它的 API：

```json
GET http://127.0.0.1:47821/api/status
{"mode": "实弹", "enabled": true, "dry_run": false, "action": "block_and_kill", ...}
```

**曾经处于实弹档**（会真掐断 + 防火墙隔离程序）。

配置里与昆明相关的红线：

| 配置项 | 值 |
|:--|:--|
| `blocked_countries` | `["CN"]` |
| `blocked_regions` | `yunnan`, `kunming`, `云南`, `昆明` |
| `blocked_cidrs` | 21 条云南/昆明 ISP 网段（222.172.0.0/16、220.163.0.0/16 …） |
| `tunnel_cidrs` | `198.18.0.0/15` |
| `allow_processes` | 只有 iKuuu 三件套 + crashpad |
| `action` | `block_and_kill`（防火墙封杀 + `SetTcpEntry` 强杀已建连接） |

历史事件里确实有过：

```
"已封杀 ...python.exe 的全部出站流量（防火墙已是启用状态）"
```

（那几次是它自己的验收测试，但**说明它会真的封杀 python.exe** —— 我们的工具就跑在 python 上。）

> 当前状态：进程/计划任务/防火墙规则都已清空 —— 它自己验收收尾时清掉了，现在没在跑。

## ★ 决定性验证：我们的连接走没走隧道

做了个实测：开一条到代理池入口 `us.proxy.example:3010` 的连接并保持，看**本地地址**绑在哪：

```
[hold] 目标 us.proxy.example:3010
[hold] 解析 -> 198.18.0.37                                    ← TUN 的 fake-ip
[hold] TCP 已建立  local=('198.18.0.1', 56082)                ← ★ 隧道内，不是物理网卡
[hold] SOCKS5 握手/认证/CONNECT 全通
[hold] 响应: {"query":"217.178.206.15"}                       ← 出口 IP 正常
```

**结论：我们的代理连接走的是隧道，`LocalAddr = 198.18.0.1`，不会被闸门判为泄漏，也不会暴露昆明 IP。**

原因：iKuuu 的 TUN 劫持了 DNS，把 `us.proxy.example` 解析成 fake-ip（`198.18.x.x`），
于是这条连接在网络层就被塞进隧道了。

## 我们做的三道自查（不依赖闸门是否开着）

把 EgressGuard 的判据搬进我们自己的工具 —— **它开着我们受它保护，它关着我们自己查**。

`egress_guard.py` v2：

| # | 检查 | 判据 |
|:--|:--|:--|
| 0 | EgressGuard 闸门状态 | 查 `/api/status`；实弹档 + 隧道断 → 拒绝开工 |
| 1 | 代理端口 | 7890 没监听 → 拒绝（**宁可停工，绝不裸连**） |
| 2 | ★ **隧道绑定自查** | 实测连一次代理入口，看 `getsockname()[0]` 在不在 `198.18.0.0/15` 里；不在 → 拒绝 |
| 3 | 出口 IP 归属 | 经代理查出口 IP，是国内 → 拒绝 |

实测输出：

```
[egress] 未检测到 EgressGuard 闸门（没装或没在跑）
[tunnel] us.proxy.example:3010       本地地址=198.18.0.1       OK 隧道内
[egress] 出口 IP = 203.0.113.20
[egress] 归属     = Hong Kong / Yau Tau Tsim Mong District / Mong Kok  (HK)
[egress] ✅ 三项全过：代理在跑 / 连接走隧道 / 出口不在国内
```

界面上的「环境自检」也会把这三条逐条打出来。

## 一条重要的设计决定：**绝不把自己加进闸门白名单**

最省事的做法是把自己的 exe 名加进 EgressGuard 的 `allow_processes`。**但不能这么做**：

> 白名单 = 把保护关掉。我们要的恰恰是**被它保护** ——
> 万一隧道断了，我们的流量会裸奔，那时**必须被它掐断**。

所以我们选择：**不改闸门的配置，改用同一个判据自查**。两边独立，互为冗余。

## 红线总结

| 红线 | 谁来保证 |
|:--|:--|
| 不用昆明 IP 出站 | ① EgressGuard 闸门 ② 我们的隧道绑定自查 ③ 出口 IP 归属检查 |
| 不暴露本机指纹 | ① 每账号独立指纹（20 套两两不同）② EgressGuard 的指纹信道封堵 |
| 不裸连目标站 | netguard 强制代理（底层拦，不靠自觉） |
| 断隧道不泄漏 | EgressGuard 熔断 + 我们的开工前拒绝 |
