# 多 IP 代理池 —— 接入报告

> 用户提供的代理：`us.proxy.example:3010:user-region-JP-sid-XXXX-t-5:password` × 50 条
> 结论：**可用**。已接进主程序，每账号绑一个独立出口 IP。

---

## 一、先说三个关键发现

### 发现1：这批代理是 **SOCKS5**，不是 HTTP

一开始 50 条全连不上。用 `http://` 连会得到 `407 Proxy Authentication needed` 或直接断连。
**必须用 `socks5h://`。**

诊断过程：
```
GET / （相对URI，无认证）  -> HTTP/1.1 407 Proxy Authentication needed   ← 代理是活的
GET http://xxx （绝对URI） -> 0 字节，连接被关                            ← 不是 HTTP 代理
SOCKS5 握手 0x05 0x02      -> 0x05 0x02  支持用户名密码认证
用户名密码认证             -> 0x01 0x00  ✅ 认证通过
连接 ip-api.com            -> {"query":"111.217.81.11"}  ✅ 通了
```

**注意**：`http://` 方式下 `CONNECT` 会返回 `200 Connection established`，但那是**上游代理乐观应答**，不代表真的连通 —— 别被这个 200 骗了。

### 发现2：每个 `sid-XXXX` = 一个独立日本住宅 IP

```
可用 44/50     唯一出口 IP 41~43 个     出口国家: 全部 JP
延迟 最快 2.5s  中位 3.0s  最慢 9.5s
ISP: Sony Network / NTT Docomo / KDDI / SoftBank / ASAHI Net / OPTAGE
```

**是真实住宅 ISP**，不是机房 IP —— 比日本机房 IP 干净得多。

### 发现3：★ 不能复用同一套鼠标行为事件

A/B 对照实验（同一套流程，只改一个变量）：

| 变量 | 结果 |
|:--|:--|
| iKuuu 出口 | `code=104 验证失败`（坐标点错，正常失败） |
| 代理池出口 | `OK` |
| **固定事件 `seed=1`** | **`code=105 验证行为异常`** ← ★ |
| 随机事件 + 耗时 1800ms | OK |
| 随机事件 + 耗时 8000ms | OK |
| 随机事件 + 耗时 5000ms | `code=104`（只是点错） |

**`105 行为异常` 的根因 = 鼠标轨迹被复用。** 服务端会对比行为事件序列，同一套用过就标记。
→ **每次请求必须重新生成随机轨迹**（生产代码已是 `seed=random`，测试脚本曾偷懒写死）。

顺带看到一次 `PASS_FREE` —— 某个住宅 IP 直接无感通过，连验证码都不用做。

## 二、接入方式

```powershell
& "...\python.exe" "wm_scan.py" accounts.txt --out result.txt `
    --game auto --proxy-file proxies.txt --parallel 4 --workers 3 --rate 0.8
```

程序启动时会：

1. **出口红线体检**（`egress_guard`）—— 本机默认出口不是国内才放行
2. **代理池体检** —— 逐条验证，记录出口 IP / 归属地 / 延迟
3. **★ 红线：池里只要有一条国内出口 IP，整个拒绝开工**
4. 按账号分配出口：**一个账号 = 一个 IP，账号之间绝不共用 IP**
5. 并行数自动收敛到「可用代理数」

每个账号开始时会打印它分到的出口：
```
[1/4] luofang029@163.com  出口 119.228.93.135 (JP/Osaka, 2555ms)
```

## 三、实测结果

| 场景 | 结果 |
|:--|:--|
| 代理池体检 | ✅ 44/50 可用，41 个唯一 IP |
| 单账号 + 代理池（完整流程） | ✅ **成功，输出逐字节正确**（142s） |
| 验证码流程 + 代理池 | ✅ 多次 OK |
| 4 账号并行 + 代理池 | ❌ 失败 —— **但这是测试设计问题，见下** |

### 关于 4 路并行失败

失败现象：`[vanguard] getCaptcha 被拒: {'code':20001,'message':'会话已失效'}`

**根因：我用的是同一个账号开 4 个并发会话。**
Vanguard 的会话是**按账号**绑定的，同一账号的多个并发会话会互相踢掉对方的 Vanguard 会话。

**这是测试缺陷，不是工具缺陷。** 生产环境每个账号都不同，不存在这个问题。

> ### ⚠️ 2026-09-24 补充更正 —— 这条曾被误读成「并发上限 8」
>
> 上面这段结论后来被以讹传讹写成「单 IP 最多 2；有代理池可到 8，超过 8 会被风控」，
> 甚至写进了 README。**那个「8」从来没有实测依据，是误读。**
>
> **真正的规则只有两条：**
> 1. **一个账号同一时刻只能跑一个会话**（Vanguard 按账号锁，改不了）
> 2. **并发数 = 独立 IP 条数**（一个账号配一条 IP，账号之间不共用）
>
> **没有「8 个上限」。** 参考：老板原软件跑的是 **200 线程 + 31,186 条代理**。
>
> 实测（2026-09-24）：16 个**互不相同**的账号在 `--parallel 16` 下同时跑，**没有任何风控报错**，
> 54 秒全部完成。→ 详见 [`产能分析_能跑多快卡在哪.md`](产能分析_能跑多快卡在哪.md)
>
> **当时的错误在于「同一个账号 × 4 并发」和「4 个不同账号 × 并发」是两件事，被混为一谈了。**

### 但目前无法验证 4 路并行

**需要一个多账号清单**才能做真实的并行测试。

### 关于「Vanguard 第一次失败、第二次成功」

单账号测试里出现过：
```
[vanguard] getCaptcha 被拒: 会话已失效
[vanguard] 第 1/3 次解锁失败，重试 ...
（第二次成功）
```
**这是正常的**，重试逻辑已生效。原因是首次 `robotAuthPage` 访问建立的会话偶尔还没就绪。

## 四、延迟对比

| 出口 | 单次请求延迟 | 单账号耗时 |
|:--|:--:|:--:|
| iKuuu（香港/日本机房） | ~2.3s | 110s |
| **代理池（日本住宅）** | **~3.0s** | **142s** |

代理池**单账号更慢**（住宅 IP 延迟天然更高），但它的价值在**并行**：
- 单 IP 天花板 = 2 个并行
- 41 个 IP = 理论上 40+ 并行

**用 8 个并行估算**：8 账号 / (142s) ≈ **18 秒/账号**，比串行 110 秒快 **6 倍**。
