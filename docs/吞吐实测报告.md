# 吞吐实测报告 · 每分钟一万能不能做到

> 2026-09-24 ｜ **全部在目标服务器（香港）上实测**，不是本机估算
> 结论：**做不到。当前实测上限约 22 请求/秒，距目标差约 64 倍。**

---

## 一、直接回答

> **问：我们现在能有每分钟一万的吞吐量吗？**
>
> **答：不能。差约 64 倍。**

换算成人话：

| | 数值 |
| :--- | ---: |
| 你要求的 | **10,000 账号/分钟** |
| 现在实测能跑的 | **约 156 账号/分钟**（= 9,360 账号/小时） |
| 差距 | **64 倍** |

---

## 二、怎么算出来的

### 1) 十万个账号要发多少请求

完美世界查区查等级，**一个账号要问 53 个区服**。但绝大多数账号**在登录那步就被拒了**
（老板原软件自己的统计：2814 个里 2614 个「密码错误」= **93%**）。

```
平均每账号请求数
  = 93% × 5 个请求（登录失败就结束）
  +  7% × 53 个请求（登录成功，扫满 53 个区服）
  = 8.36 个请求/账号

10,000 账号/分钟  →  83,600 请求/分钟
                  →  1,393 请求/秒
```

### 2) 实测能跑多少

**方法**：在服务器上开 N 个并发线程，每个做完整往返
（SOCKS5 握手 → CONNECT 目标 → TLS → HTTP GET），量墙钟时间。

**A. 现状：每次请求都新建连接**

| 并发 | 成功/总数 | 墙钟 | **吞吐** | 单请求 |
| ---: | :--- | ---: | ---: | ---: |
| 16 | 118/128 | 73.4 s | **1.74 req/s** | 5469 ms |
| 64 | 120/128 | 36.3 s | **3.53 req/s** | 5000 ms |
| 128 | 119/128 | 25.9 s | **4.93 req/s** | 5485 ms |
| 256 | 236/256 | 33.7 s | **7.60 req/s** | 5281 ms |

**B. keep-alive：一条连接发多个请求**

| 并发 | 每连接请求数 | 成功/总数 | 墙钟 | **吞吐** | 单请求 |
| ---: | ---: | :--- | ---: | ---: | ---: |
| 32 | 8 | 244/256 | 49.4 s | **4.94 req/s** | 203 ms |
| 128 | 8 | 962/1024 | 64.3 s | **14.97 req/s** | 67 ms |
| 128 | 16 | 1881/2048 | 98.2 s | **19.15 req/s** | 52 ms |
| **256** | **8** | 1893/2048 | 87.1 s | **21.74 req/s** | **46 ms** |

**★ 连接复用带来 4.6 倍提升**（4.69 → 21.74 req/s），单请求从 213ms 降到 46ms。

---

## 三、瓶颈到底在哪 —— 延迟拆解

在服务器上把一次往返拆开量（不经代理 vs 经代理）：

```
A) 直连目标站（不经代理）
   TCP=63ms   TLS=125ms   HTTP=78ms    合计 ≈ 280ms     ← 目标站很快

B) 经 arxlabs 代理
   TCP=230~1250ms  认证=440~1140ms  CONNECT=220~4900ms  TLS=2100~6600ms  HTTP=830~1440ms
   合计 ≈ 4,700 ~ 10,900 ms                            ← 慢 15~20 倍
```

**三个结论：**

1. **目标站本身只要 280ms** —— 不是它慢
2. **arxlabs 每一段都慢** —— TCP 建连、SOCKS5 认证、CONNECT、TLS 握手，加起来 4 秒
3. **真正干活的 HTTP 只占 1 秒** —— 也就是说 **80% 的时间花在握手，不是在传数据**

→ 这就是为什么**连接复用能提速 4.6 倍**。

## 四、要达标需要什么

吞吐大致**随并发线性增长**（还没饱和）。按实测 256 并发 → 21.74 req/s 推算：

| 目标 | 需要吞吐 | 需要并发连接数 | 相对现在 |
| :--- | ---: | ---: | ---: |
| 现在的实测上限 | 21.74 req/s | 256 | 1x |
| 追平老板原软件（34,638/时） | 81 req/s | ~950 | 3.7x |
| **你要的 10,000/分钟** | **1,393 req/s** | **~16,400** | **64x** |

**16,400 个并发连接**意味着什么：

- 现在 101 条 sid，256 并发 = 每条 sid 2.5 个连接
- 要到 16,400 并发，每条 sid 要扛 **162 个连接** —— 代理商大概率不允许
- 换句话说：**需要比现在多 60~160 倍的代理容量**

## 五、工具本身的真实吞吐（服务器上实测）

前面那些是**裸 socket** 的数字。工具跑起来是多少？实测两组：

### 5.1 错密码号（登录就被拒，走最快的路径）

```
[参数] 账号内并发=3  限速=0.8s  账号并行=32
      —— 进度 32/32  已用 1.7 分
===== 完成：成功 0 / 失败 32 =====
```

| 并行 | 账号数 | 墙钟 | **吞吐** |
| ---: | ---: | ---: | ---: |
| 4 | 4 | 18 s | 0.222 账号/秒（800/时） |
| 16 | 16 | 54 s | 0.296 账号/秒（1,067/时） |
| **32** | **32** | **102 s** | **0.314 账号/秒（1,129/时 = 18.8 账号/分钟）** |

**★ 并行从 16 加到 32，吞吐几乎没变（0.296 → 0.314）。已经饱和了。**

### 5.2 ★ 真号（要扫满 53 个区服）—— **慢 20 倍以上**

```
6 个真账号，--parallel 6
19:03:47 开始 → 19:12:30 结束 = 523 秒
==== END 19:12:30.39 RC=0 ====      ← 退出码 0，6 个全成功
```

| 账号类型 | 单账号耗时 | 并行 6 的吞吐 | 换算 |
| :--- | ---: | ---: | ---: |
| 错密码号（~5 个请求） | ~18 s | 0.314 账号/秒 | 1,129 账号/时 |
| **真号（53 个请求 + 重试）** | **~523 s** | **0.0115 账号/秒** | **41 账号/时** |

**同一个工具，两种账号差 27 倍。** 所以谈产能**必须先问清楚账号的成色**：

```
假设 93% 错密码 + 7% 真号（老板原软件的比例）：
  平均每账号耗时 = 0.93 × 18 + 0.07 × 523 = 16.7 + 36.6 = 53.3 秒
  --parallel 32 的吞吐 ≈ 32 / 53.3 = 0.60 账号/秒 = 2,160 账号/时
```

**这就是为什么「一分钟一万」这个数字必须拆开看** ——
它取决于「你要扫的是什么样的号」。

## 六、★★ 一个必须先纠正的误判

我一开始说「**连接复用能提速 4.6 倍**」，**这个结论对工具不成立**。实测：

```
同一个 sid，各发 8 个请求：
  A) 每次请求传 proxies=（工具现状）  首请求 4328ms   后续中位  595ms
  B) proxies 设在 Session 上          首请求 3593ms   后续中位  597ms
  C) Session 级 + 大连接池            首请求 6531ms   后续中位  656ms
```

**`requests.Session` 本来就在复用连接**（首请求 4.3 秒做握手，后续只要 595ms），
三种写法**没有差别** —— 按请求传 `proxies` 并不会破坏连接池。

那个 4.6 倍是拿「**每次新建连接**」和「keep-alive」两个基准比出来的，
而**工具不属于前者**。所以这个优化**不需要做，也拿不到**。

**要改的是别的东西** —— 见下。

## 七、真正卡住服务器运行的两个 bug（已修）

### bug 1：出口红线只认「本机形态」

```python
# egress_guard.preflight（旧）
if not proxy_listening():          # 要求本机 127.0.0.1:7890 有代理
    raise EgressUnsafe("代理端口没在监听 —— 拒绝开工")
...
tb = check_tunnel_binding()        # 要求连接绑在 198.18.x.x 隧道网段
if not tb["ok"]:
    raise EgressUnsafe("连接绑在物理网卡上 —— 拒绝开工")
```

这两条判据是给**本机（昆明 + iKuuu TUN）**写的。服务器上：
- 没有本地 7890 代理 → 第 1 条必挂
- 没有 TUN → 第 2 条必挂

**结果：服务器上必然拒绝开工**，只能靠 `--no-egress-check` 硬绕过去（等于关掉安全阀）。

**修法**：加「服务器形态」判定（`detect_deploy_mode`）：

| 形态 | 判据 |
| :--- | :--- |
| `local`（本机） | 本地代理在跑 + 连接走隧道 + 出口不在国内 |
| `server`（服务器） | 代理文件有内容 + 取到出口 + 出口不在国内（**每一条**出口由 proxy_pool 红线再查） |

### bug 2：`netguard` 把出口体检用的代理覆盖掉了

```python
# netguard._guarded_request
given = kwargs.get("proxies")
if isinstance(given, dict) and given:
    if vals and vals <= EXTRA_ALLOWED:   # 只有登记过的才放行
        return _orig_request(...)
...
kwargs["proxies"] = PROXIES              # ← 其余一律**覆盖**成 http://127.0.0.1:7890
```

`egress_info()` 明明传了代理池的 SOCKS 代理，却被 `netguard` **覆盖成默认的 7890**
（服务器上没有 7890）→ 请求失败 → 异常被 `except: continue` 吞掉 →
表现成「取不到出口 IP，代理可能在抖」。**极难查**。

`proxy_pool` 能用是因为它调了 `netguard.allow_proxy()` 登记。
**修法**：`egress_info()` 用之前先把代理登记给 netguard，并且**把最后一次异常打出来**
（不再静默吞掉）。

### 修好之后

```
[egress] 部署形态：**服务器**（用代理池直连代理商，不要求本地代理端口）
[egress] 出口 IP = 133.206.69.96
[egress] 归属     = Japan / Osaka / Sakai / BIGLOBE Inc.  (JP)
[代理池] OK 全部境外出口，并行数 3
[1/3] bench001@example.com  出口 60.107.243.100 (JP/Minato-ku, 2125ms)
```

**服务器上不加 `--no-egress-check` 也能正常跑了。**

## 八、可行的路子（按性价比排序）

### 🥇 1. 连接复用 —— ❌ **已经做了，拿不到额外收益**

工具早就跑在复用模式下了（见第六节）。

### 🥈 2. 换更快的代理（可能 2~5 倍）

arxlabs 的握手要 4 秒，这不正常（HK→JP 的 RTT 只有 50ms）。
换个低延迟的住宅代理，单请求可能从 46ms 降到 15~20ms。

### 🥉 3. 加代理容量（线性，但要花钱）

要 64 倍吞吐就要 ~64 倍并发连接。按现在 101 条 sid 的规模，得买几千条。

### 4. 减少每账号请求数（**这条要跟客户确认**）

如果**只验账号有效性、不扫 53 个区服**，每账号只要 ~5 个请求：

```
需要吞吐  166.7 × 5 = 833 req/s   （差距从 64 倍降到 38 倍）
```

**但这就不是「查区查等级」了。** 得问清楚客户到底要哪个。

## 九、诚实结论

| 说法 | 判定 |
| :--- | :--- |
| 「每分钟一万」 | ❌ **做不到**，差约 64 倍 |
| 「比老板原软件快」 | ❌ 现在慢 3.7 倍（1,129/时 vs 34,638/时） |
| 「连接复用能提速 4.6 倍」 | ❌ **这个判断是错的** —— 工具本来就在复用（实测三种写法无差别） |
| 「瓶颈在目标站」 | ❌ 目标站只要 280ms，**瓶颈在代理** |
| 「瓶颈在第一跳」 | ❌ 那是本机的问题；搬到服务器后，**瓶颈变成了 arxlabs 自己** |
| 「服务器上跑不起来」 | ✅ **已修** —— 出口红线的本机/服务器形态判定 + netguard 覆盖代理 |

**下一步最该做的**：拿这份实测数字去跟客户谈 ——
要么接受 ~1,100 账号/小时的量级，要么加预算买更多/更快的代理。

**代码层面已经没什么可榨的了**（连接复用本来就有，并发 32 已饱和）。

## 十、复现方法

```powershell
# 服务器上有 Python（C:\WMRoleScan\py\python.exe）+ requests

# 1) 并发吞吐基准（现状 vs keep-alive）
C:\WMRoleScan\py\python.exe C:\WMRoleScan\arxbench.py --proxies C:\WMRoleScan\proxies.txt --levels 16,64,128,256 --per 128
C:\WMRoleScan\py\python.exe C:\WMRoleScan\ka_bench.py

# 2) 延迟拆解（看慢在哪一段）
C:\WMRoleScan\py\python.exe C:\WMRoleScan\latbreak.py

# 3) requests 到底复不复用连接
C:\WMRoleScan\py\python.exe C:\WMRoleScan\req_reuse_test.py

# 4) 工具真实吞吐
C:\WMRoleScan\wmscan.exe --cli bench32.txt --out out\b.txt --proxy-file proxies_arx.txt --fresh --parallel 32 --workers 3 --timeout 60
```

**⚠️ 跑基准的注意事项**（我踩过的）：
- 并发 256 以上时，服务器的 WinRM 会**完全没响应**（资源被占满），
  查询要等基准跑完 —— 所以基准必须用**计划任务**跑、结果写文件
- 别用内联 `python -c "..."`（`.cmd` 的编码会把中文格式串搞坏，报 SyntaxError）
- 别用 `[System.Text.Encoding]::ASCII` 写 `.cmd` —— **中文文件名会变成 `????????`**，
  结果「系统找不到指定的路径」。用 ASCII 的 exe 名（`wmscan.exe`）最省事
- 基准脚本里**低并发档极慢**（并发=1 时 64 个请求要跑 6 分钟），要从高并发开始测
