## 二、TUN 让所有端口扫描变成假象

### 现象

之前排查服务器时看到「22 / 445 / 3389 / 5985 **全部开放**」，据此判断「机房防火墙在应答」。
**这个判断是错的 —— 那个观察本身就是假的。**

### 根因

本机默认路由走 **iKuuuVPN 的 TUN 网卡**（fake-ip 模式，`198.18.0.0/16`，网关 `198.18.0.2`）：

```
Get-NetRoute -DestinationPrefix 0.0.0.0/0
  ifIndex NextHop     RouteMetric InterfaceAlias
        9 198.18.0.2            0 iKuuuVPN        ← 默认路由
       24 192.168.0.1           0 WLAN 3
```

这个 TUN 对**任何** TCP 连接都会**在本地立刻假装握手成功**，然后把不支持的端口直接黑洞。

### 铁证：拿不存在的 IP 去连

| 目标 | :22 | :3389 | :445 | :80 | :443 | :12345 |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| **154.219.105.203（真目标）** | 0.001s 假通 | 0.001s 假通 | 0.001s 假通 | 0.014s 假通 | 0.001s 假通 | 0.001s 假通 |
| `203.0.113.7`（**测试保留地址**） | 0.016s 假通 | 0.001s 假通 | 0.001s 假通 | 0.001s 假通 | 0.001s 假通 | 0.001s 假通 |
| `192.0.2.99`（**测试保留地址**） | 0.001s 假通 | 0.015s 假通 | 0.016s 假通 | 0.001s 假通 | 0.001s 假通 | 0.015s 假通 |

> 连**根本不存在的主机**都「全端口开放」—— 所以之前的端口扫描**一条有效数据都没有**。

### 对照：换成物理网卡直连（源地址绑 `192.168.0.101`）

| 目标 | 结果 | 说明 |
| :-- | :-- | :-- |
| `223.5.5.5:443` | ✅ 真连上 0.083s | 国内正常 |
| `114.114.114.114:53` | ✅ 真连上 0.065s | 国内正常 |
| `198.44.166.3:3010` | ✅ 真连上，返回真实 HTTP 响应 | 美国可达 |
| `1.1.1.1:443` / `8.8.8.8:443` | ❌ 超时 | 国内正常现象 |
| **`154.219.105.203`** 全端口 | ❌ **全部超时** | ← 见第五节 |

### 更隐蔽的一层：HTTP 代理的「乐观 200」

`iKuuuVPNCore`（`127.0.0.1:7890`，香港出口）是 HTTP 代理。它收到 `CONNECT` 后
**不管目标死活都回 `200 Connection established`**，然后才去连。

所以：

```
CONNECT 154.219.105.203:3389  →  HTTP/1.1 200 Connection established   ← 假的！
                              →  然后 0 字节，永远等不到 RDP 回复
```

**「CONNECT 成功」完全不能证明目标在线。** 唯一可靠办法是发一个**真协议请求**看有没有真回复 ——
这就是 `tools/tunnel.py` 里 `probe_target()` 干的事：

| 端口 | 判活方式 |
| :-- | :-- |
| 443 / 8443 / 5986 | 真 TLS 握手（拿 `version()`） |
| 3389 | 发 RDP TPKT（`030000132ee0...`）等回复 |
| 445 | 发 SMB1 negotiate |
| 80 / 5985 | 发 HTTP 请求 |
| 22 / 25 / 110 / 21 / 3306 / 6379 | 等服务端自己先报 banner |
| 其它 | 依次试 banner / SOCKS5 问候 / 换行 |

实测这个判活器是对的：

```
[不通]  154.219.105.203:3389   -> 9ms,  [无任何回应]              ← 真话
[通]    passport.wanmei.com:443 -> 14ms, [TLS 握手成功] TLSv1.2   ← 真话
[通]    198.44.166.3:3010      -> 22ms, [有真回应] 0500           ← SOCKS5 问候应答
[通]    github.com:443         -> 11ms, [TLS 握手成功] TLSv1.3
```

## 三、代理池拒绝大陆 IP —— 及解法

### 现象

arxlabs 代理池（SOCKS5，`us.arxlabs.io:3010`）**从本机直连一律被拒**：

```
HTTP/1.1 403 Forbidden
Proxy-Authenticate: Basic realm="proxy"

msg: forbidden ip=220.197.230.134 not supported
```

`220.197.230.134` = **本机物理出口 IP（昆明）**。

### 为什么之前没发现

`docs/PROXY_POOL.md` 已经写过「**这批代理是 SOCKS5，不是 HTTP**」，
但用 HTTP `CONNECT` 去连时，**上游会乐观返回 `200 Connection established`**，
看起来像通了，实际是被掐断。所以诊断时反复在「到底通不通」上打转。

**这次的决定性动作：直接做 SOCKS5 握手。**

```
① 直连（昆明 IP）           → 服务器回 "HT..."（HTTP 403 文本）  ✗
② 经 127.0.0.1:7890（香港） → \x05\x01\x02 → \x05\x02 → 认证 → OK  ✓
```

### 可用链路

```
本机 → 127.0.0.1:7890（iKuuu VPN，香港出口 103.151.172.36）
     → 198.44.166.3:3010（arxlabs SOCKS5）
     → 日本住宅 IP
     → 目标站
```

**实测出口（3 个 sid）**：

| sid | 出口 IP | 归属 |
| :-- | :-- | :-- |
| ApJFvYFH | `106.146.215.4` | Osaka / AS2516 KDDI |
| QqUXUeT1 | `59.132.67.253` | Tokyo / AS2516 KDDI |
| JFd75SCb | `106.155.11.40` | Tokyo / AS2516 KDDI |

**目标站验证**：

```
GET passport.wanmei.com/sso/servlet/ajax?op=mCaptchaInit&isAICap=1
→ HTTP/1.1 200
→ {"data":{"appId":"10003","capTicket":"ced3dce618fc4fdcb80048e353421d37"},"code":0}
```

昆明 IP 全程不出现。

### 解法：`tools/chain_proxy.py`

把这条链**封装成普通的本地 SOCKS5 代理**，每条 sid 一个本地端口：

```
127.0.0.1:20001  →  sid-ApJFvYFH  →  106.146.215.4  (Osaka/KDDI)
127.0.0.1:20002  →  sid-QqUXUeT1  →  59.132.67.253  (Tokyo/KDDI)
...
```

于是 `proxy_pool.py` **一行都不用改**，只要把代理文件换成：

```
127.0.0.1:20001::
127.0.0.1:20002::
```

```powershell
# 启动桥接
python tools\chain_proxy.py --proxies 代理.txt --first-hop 127.0.0.1:7890
# 它会写出 proxies_local.txt，直接喂主程序
python src\wm_scan.py 账号.txt --proxy-file proxies_local.txt
```

**实测（8 条）**：

### 注意

- **第一跳必须境外。** 换成本机直连立刻被拒。
- 延迟偏高（快的 2.6s，慢的 28s）。慢的那几条可能是 sid 冷启动，
  也可能是住宅 IP 本身慢 —— 生产时按延迟排序取用即可。
- 桥接器体检里只要出现 **CN 出口会直接剔除**，不写进输出文件（延续原有红线）。

## 四、顺带修掉的一个真 bug

`tools/chain_proxy.py` 和 `tools/tunnel.py` 里都有这个模式：

```python
def say(*a):
    try:
        print(*a, flush=True)
    except Exception:
        pass          # ← 为了"日志不要打断主流程"
```

而 Windows 控制台默认是 **GBK**。日志里只要出现一个非 GBK 字符（`✗` `★` `→`），
`print` 就抛 `UnicodeEncodeError`，**被 `except` 静默吞掉 —— 整行日志凭空消失。**

实际踩到：`tunnel.py` 的探活结果整段不打印，排查了半天。

**修法**（两个工具都已加）：

```python
for _s in (sys.stdout, sys.stderr):
    try:
        _s.reconfigure(encoding="utf-8", errors="replace")
    except Exception:
        pass
```

> 教训：**日志函数不要吞异常。** 至少该写 `sys.stderr.write` 兜底。

## 五、服务器 `154.219.105.203` 的真实状态

### 结论：**机器本身没起来。** 不是网络问题，不是端口问题，不是 GFW。

### 证据一：本机物理网卡直连（绕开 TUN）

```
154.219.105.203:3389  FAIL TimeoutError
154.219.105.203:80    FAIL TimeoutError
154.219.105.203:443   FAIL TimeoutError
154.219.105.203:22    FAIL TimeoutError
154.219.105.203:445   FAIL TimeoutError
154.219.105.203:5985  FAIL TimeoutError
控制组 198.44.166.3:3010  OK 0.26s        ← 美国 IP 正常，不是"国内出不去"
```

### 证据二：第三方全球节点（check-host.net）

| 测试 | 节点 | 结果 |
| :-- | :-- | :-- |
| TCP :3389 | 西班牙 / 芬兰 / 印度 / 伊朗 / 葡萄牙 / 新加坡 / 保加利亚 / 罗马尼亚 / 美国 | **全部 Connection timed out** |
| ICMP ping | 巴西 / 以色列 / 伊朗×3 / 荷兰 | **全部 TIMEOUT** |
| 对照组 TCP `1.1.1.1:443` | 芬兰 / 匈牙利 / 哈萨克 | ✅ 0.002~0.028s |

**从 15 个分布在全球的独立节点看，这台机器都不可达。**

### 归属信息

```
154.219.105.203  →  香港 (Tung Chung / Islands)
                    AS401701 cognetcloud INC
```

### 因此

- 这台机器 **没开机 / 没装完 / 没分配 IP**，需在**商家控制台**处理。
- 重装系统后有些商家会**把实例停在「已停止」**，需要手动开机。
- 重装后 **IP 有可能变**，要核对。

### 怎么确认（网页控制台是唯一确定能用的通道）

商家控制台的 **Web VNC / 网页控制台**走 443，
而 iKuuu 的 TUN **放行 80/443**（实测 443 能跑完 TLS 拿到真实 HTTP 200），
所以**网页控制台能穿过 TUN 正常用**。

### 机器起来后怎么连

```powershell
# 方案 A：走香港出口（服务器看到香港 IP，昆明 IP 不暴露）
python tools\tunnel.py --map 13389:154.219.105.203:3389 --first-hop 127.0.0.1:7890
mstsc /v:127.0.0.1:13389

# 方案 B：直连（要先关 iKuuu VPN；服务器看到昆明 IP，自己的服务器可接受）
python tools\tunnel.py --map 13389:154.219.105.203:3389 --first-hop none
```

`tools/tunnel.py` 启动时会先做**权威探活**（真 TLS / 真 RDP 握手），
直接告诉你目标到底通不通，不会被代理的「乐观 200」骗。
